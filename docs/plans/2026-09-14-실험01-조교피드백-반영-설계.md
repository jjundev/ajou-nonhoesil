# 실험01 조교 피드백 반영 — 표 열 보존과 신호 이름 표기 (설계)

2026-09-13 `/grill-yourself` 로 만든 설계를 2026-09-14 스크래치 프로토타입 실측으로 고친
판이다. 구현 계획은 `docs/plans/2026-09-14-실험01-조교피드백-반영-구현계획.md`.

## 배경

조교가 실험01 예비보고서에 두 항목으로 -2점을 줬다.

1. 실험 예상 결과의 논리표가 잘못 작성됨(-1). 실험 회로도의 출력인 L1 과 L2 를 표에 보여 줘야 한다.
2. 실험 회로 결선도에 입력 A·B·C 위치 표기가 없어 확인하기 어려움(-1).
3. 다음 주에 우수 예비보고서를 보여 줄 테니 참고해서 회로 결선도를 작성하라는 안내.

원인은 이미 추적했다.

- **표 열 누락은 예보 작성 단계에서 생겼다.** 명세 T1~T4 는 처음부터 `A B C L1 L2` 다섯 열이다.
  write-pre-report 첫 출력부터 `A B C Y` 네 열이었고 노션 baseline v1~v11 이 전부 같다. 스킬에는
  "명세의 표 전부" 만 있고 열 보존 규칙이 없었다. 규칙 13 의 인용 예시 `Y = A·B·C` 가 `Y` 표기를
  굳혔다. review-lab-report 는 행 수만 대조해 놓쳤다.
- **입력 표기 누락은 원도→손그림 전사에서 생겼다.** 원도는 입력 이름을 보드 밖(x=12) 꼬리표
  `입력 A → b7` 에만 적었다. breadboard-diagram §4 가 "보드 위에는 두 글자 꼬리표만" 으로 정한
  결과다. 학생은 보드 판형 위만 따라 그려 그 글자가 옮겨지지 않았다. review-hand-diagram 에는
  이름 표기를 보는 항목이 없었다.

## Intent

조교가 감점한 두 항목이 실험02 이후에 다시 나오지 않도록 하네스 네 스킬에 규칙과 기계 검사를
넣는다. 예비보고서의 예상 결과 표는 명세 표의 열 이름·열 수·열 순서·셀을 그대로 옮기고,
write-pre-report·review-lab-report 가 `validate.check_report_tables` 로 그것을 검사한다. 결선도
원도는 입력 A·B·C 와 출력 이름을 보드 안에 찍고, review-hand-diagram 이 이름 표기 누락을 H15
기능 등급으로 막는다. 부수로 실험01 예보 md 의 T1~T4 를 명세대로 되돌리고, 이번 피드백을
`docs/notion-feedback/` 에 기록한다.

Classification: **bounded** — 기존 규칙 목록·검사 함수 목록·렌더 헬퍼를 고치는 일이다.

## 완료 시 동작

- write-pre-report 가 만든 예보에서 예상 결과 표의 머리가 명세와 다르면 검증 단계에서 error 가
  뜨고, error 0 이 될 때까지 작성이 끝나지 않는다.
- review-lab-report 라운드 문서의 자동 검사 절에 표 머리·순서·셀 finding 이 나온다.
- 예보의 표 불릿 제목이 명세 `derived (…)` 의 열 이름을 쓴다. 예: `- **3-input AND** (`L1 = A·B`, `L2 = A·B·C`)`.
- 결선도 원도에 입력 `A`·`B`·`C` 가 점퍼의 레일 쪽 끝 옆에, 출력 `L1`·`L2`·`X`·`Y`·`Z` 가 LED
  옆에 보드 안 배지로 찍힌다. 보드 밖 `입력 A → b7` 꼬리표와 범례는 그대로 남는다.
- review-hand-diagram 이 전사의 `labels` 를 참조의 신호 이름과 대조한다. 빠진 이름마다 H15
  기능 finding 이 나고 판정은 "수정 필요" 다.
- 실험01 예보 md 의 T1~T4 가 `A B C L1 L2` 로 복원되고 새 검사를 통과한다.
- `docs/notion-feedback/round2-실험01-예비보고서.md` 에 두 건이 체계적 항목으로 기록된다.

## 구현 명세

### 트랙 1 · 표 열 보존

**`validate.check_report_tables(report_path, spec) -> list[Finding]`** — `check_report_references`
바로 뒤. 예비보고서 전용이다.

1. 보고서 표는 `md.parse_tables` 로 뽑고 머리·셀의 `**`·백틱을 벗긴다.
2. 명세 진리표(`kind: truth-table`, record·reference 모두) 마다 **정확 대응** 표를 모은다. 머리가
   명세 머리의 부분집합이고, 행 수가 같고, 셀이 명세의 해당 열과 전부 같은 표다.
3. record 표에 정확 대응이 있으면 두 가지를 본다. 대응 표들의 머리 합집합이 명세 머리와 같은지,
   그리고 각 표 안의 열 순서가 명세 순서를 따르는지다. §절대 규칙 19 의 표 나누기가 이 규칙으로 통과한다.
4. 정확 대응이 없으면 어느 명세 표에도 정확 대응하지 않은 표 가운데 가장 가까운 것을 짚는다.
   가깝다는 것은 행 수가 같고 머리가 가장 많이 겹친다는 뜻이고, 동률이면 앞 표를 고른다.
   머리가 부분집합이면 처음 갈리는 행을 알린다. 아니면 빠진 열과 명세에 없는 열을 한 줄로 알린다.
   짚을 표도 없으면 "대응하는 표가 없다" 를 낸다.
5. 전부 error. 조교가 실제로 감점한 항목이다.

**정확 대응을 먼저 묶는 이유 (실측).** 복원된 실험01 예보에서 T1~T4 는 모두 머리 `A B C L1 L2`
의 8행 표다. 머리와 행 수만 보고 짝지으면 명세 표 하나가 보고서 표 넷을 전부 짝으로 잡는다.
그러면 AND 표를 OR 명세로 대조해 셀 오류가 12건 헛난다. 셀까지 같은 표끼리 짝지으면 0건이다.
T2 셀 하나만 틀리게 하면 T2 한 건만 짚는다.

**write-pre-report.** §절대 규칙 22 를 추가한다. 예상 결과 표는 명세 머리를 글자 그대로 옮기고,
불릿 제목의 부울식도 열 이름으로 쓴다. 규칙 13 의 `Y = A·B·C` 인용을 지운다. §섹션별 재료
"실험 과정 및 예상 결과" 행에서 규칙 22 를 가리키고, §실행 절차 9 에서 `check_report_tables` 를 부른다.

**review-lab-report.** 설명문에 "예비보고서 표 머리 대조" 를 넣는다. §실행 절차 4 는 예보일 때만
`check_report_tables` 를 부른다.

**실험01 예보 md 복원.** T1~T4 불릿 제목과 표를 명세에서 조립해 바꾸고, 결선 절 불릿 제목의
부울식도 바꾼다. 파일은 CRLF 라 바이트로 읽고 쓴다. 실측으로 확인한 것은 네 가지다. 줄 수
347 이 그대로이고, `check_notion_markdown` error 0, `check_report_sections` 0, `check_body_style`
warn 3 이 그대로다.

### 트랙 2 · 신호 이름 표기

**렌더러 (`render_breadboard.py`).**

- `BreadboardRenderer.signal_tag(name, x, y, align='center', col=…, seg=None)` 를 추가한다.
  `font_en_bold` 로 배지를 찍고, 상자를 `self.tag_boxes` 에 `(이름, 상자, 배선 번호)` 로 남긴다.
- `_marker()` 가 번호 원 상자를 `self.marker_boxes` 에 남긴다.
- `_input_jumper()` 는 보드 밖 꼬리표를 그대로 두고, 신호 이름을 보드 안에 하나 더 찍는다.
  자리는 x = (보드 좌 테두리 149 + 좌 GND 레일 174) / 2 이고 y 는 점퍼의 레일 쪽 끝 행이다.
- `draw_led()` 의 꼬리표를 `signal_tag(label, x + 10, ymid, align='left', col=LED 색)` 으로 바꾼다.
- `wiring()` 에 `'inputs'` 를 추가한다.
- 배선 설명 `최종 출력 Y = …` 를 `최종 출력 L2 = …` 로 고친다. 결선 순서표에 인쇄되는 문구다.

**배지 자리 — 레일과 a열 사이 여백이 아니라 레일 쪽 끝 옆이다 (실측).** 처음 설계는 레일과 a열
사이 여백의 점퍼선 위였다. 프로토타입에서 두 가지가 부딪혔다. NAND 의 C 와 복합회로의 B 는
번호 원 `(215, +13)` 과 겹쳤다. 복합회로에서는 Z 급전선이 x=212 로 10~25행을 세로로 지나가
어떤 입력 배지도 그 선을 덮었다. 보드 좌 테두리와 GND 레일 사이 여백은 13개 실험01 빌더
전부에서 번호 원·배선·꽂힌 홀·다른 배지와의 충돌이 0건이었다. 레일 쪽 끝은 학생이 0/1 을
바꿀 때 옮겨 꽂는 자리라 입력 이름을 붙이기에 의미상으로도 맞다.

**가독성 테스트.** 두 가지를 추가한다. 입력 이름과 LED 꼬리표가 전부 보드 안 배지로 있는지 본다.
그리고 신호 이름 배지가 번호 원·자기 것이 아닌 배선·꽂힌 홀·다른 배지를 가리지 않는지 본다.
보드 위 배지 수는 **그림 한 장 기준**으로 센다. 단계 그림은 기준선을 얻으려고 앞 보드를 한 번 더
그리는데, 지금 테스트는 그 배지까지 합쳐 센다. 한 장에 5개인 그림이 10개로 잡혀 상한 8을 넘는다.

**손그림 검토.**

- `hand_transcript.Diagram.labels` 를 추가하고, 전사의 선택 키 `labels` 를 읽는다. 항목은
  `{"name": …, "at": 홀 주소 | 없음}` 이다.
- `hand_compare._from_wiring` 이 참조 `labels` 를 입력 이름과 LED 꼬리표로 채운다.
- `check_labels` 가 H15 를 기능 등급으로 낸다. 이름 집합만 보고 대소문자는 가리지 않는다.
- 실물 전사 픽스처 `hand_e1_nand_chip_up_one.json` 은 2026-09-09 전사라 `labels` 가 없다. 이
  픽스처로 "권장 수정 후 제출 가능" 을 단언하는 테스트는 H14·H7 을 보려는 것이다. 그래서 그
  테스트 안에서 `hand.labels = list(ref.labels)` 로 이름을 채운다. 전사 파일은 고치지 않는다.
- review-hand-diagram 문서에는 세 가지를 반영한다. 전사 예시와 규칙에 `labels` 를 넣고,
  검사 목록에 H15 행을 추가하고, 기능 등급인 이유를 적는다.
