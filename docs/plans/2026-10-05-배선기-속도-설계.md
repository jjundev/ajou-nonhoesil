# 결선도 배선기(`route_plan`) 속도 개선 — 설계

날짜: 2026-10-05. 앞 작업: `docs/plans/2026-10-05-느린-배선-테스트-엔진-공유-{설계,구현계획}.md`.

## 의도

v2 배선기의 순수 계산만 줄여서 `board_v2_e4` 그룹이 끝나는 시간, 곧 전체 스위트 시간을 줄인다. 대상은
`router.py` 의 `_on_seg`·`_ordered`/`cost` 와 `checks.py` 의 `_seg_in_box` 다. 같은 입력이면 경로 점,
번호 원 자리, 후보 순서가 한 칸도 바뀌지 않는다.

완료 조건:
- 고치기 전에 뜬 pickle 과 고친 뒤 결과가 `==` 로 같고 `repr` 도 같다.
- 안전장치 시험이 모두 녹색이다.
- 전체 스위트 3회 중앙값 ≤ 85초(같은 날, 같은 워크트리의 기준점 대비).

분류: bounded — 있는 함수의 내부만 바꾸고 인터페이스·호출 흐름은 그대로다.

## 지금 병목 (main `17981ac`)

- 전체 실행 ≈ `board_v2_e4` 그룹 시간(동시 실행 98초, 단독 약 57초). 그다음 그룹은 22초 이하.
- 경로 탐색 단독(`-n0`, 캐시 빔): MUX(λ=0.5) 28.3초, MUX(λ=0) 19.5초, DMUX 각 4.5초 안팎.
- cProfile(MUX, 비율로 볼 것): `_valid` 46%(`_on_seg` 1774만 회, `_seg_in_box` 훑기 2790만 회),
  `_ordered` 36%(`cost` 77만 회, `_clean` 91만 회, `_holes_passed` 367만 회). DMUX 는 `_ordered` 가 93%.

## 끝나면

- 시험·보고서 결선도·`place_search` 가 고르는 경로는 그대로다. 걸리는 시간만 바뀐다.
- `verify()`(R11·R14)와 `_marker_clear` 도 `_seg_in_box` 를 같이 쓰므로 함께 빨라진다. 판정은 같다.
- 동치가 깨지면 새 동치 시험(대조용 원본 함수), `LambdaZero`, `CommittedPngs_*`, 일회성 pickle 비교 중
  어디서든 걸린다.

## 이번에 안 하는 것

- `_valid` 검사 순서 바꾸기 — 1~3 뒤 다시 프로파일한 결과만 이 문서에 남긴다. 85초 기준에 못 미칠
  때만 사용자에게 물어 이번 라운드에 넣는다.
- `_clean` 메모이즈, 후보 생성 중복 줄이기 — 후보를 만드는 순서와 표현(int/float)이 `set` 이 남길
  대표값을 정한다. 위험 대비 이득이 작다.
- 경로 디스크 캐시, `slow` 마크, 비용 식이나 후보 규칙 변경.
- λ=0.5 스냅숏 커밋 — 이번 동치 증명은 일회성 pickle 로 충분하다.

## 구현

1. **`_on_seg` 범위 선검사** (`router.py:86`) — 함수 맨 앞, 길이 계산 전에:
   ```python
   if not (min(a[0], b[0]) - 2 < p[0] < max(a[0], b[0]) + 2 and min(a[1], b[1]) - 2 < p[1] < max(a[1], b[1]) + 2):
       return False
   ```
   원래 식이 참이면 `0 < along < L` 이고 수직 거리 `|s| < 1.5` 라서 `p` 의 각 좌표는 구간 범위 ±`|s|`
   안이다(대각선도). 수직 거리는 나눗셈으로 재므로 1.5 근처에서 반올림이 끼어든다 — 0.5px 여유로 덮는다.
2. **`_seg_in_box` 범위 선검사** (`checks.py:74`) — 훑기 전에:
   ```python
   if max(a[0], b[0]) < x0 - 1 or min(a[0], b[0]) > x1 + 1 or max(a[1], b[1]) < y0 - 1 or min(a[1], b[1]) > y1 + 1:
       return False
   ```
   훑는 점 `a + (b-a)*t/n` 은 반올림 때문에 끝점보다 ulp 만큼 밖에 놓인다 —
   `0.7000000000000001 + (1.8 - 0.7000000000000001) == 1.8000000000000003`. 그래서 왼쪽 변이 1.8 인
   상자를 원래 함수는 "안"이라고 본다. 딱 맞는 경계로 일찍 끝내면 이 답이 바뀐다 — 1px 여유를 둔다.
   겹칠 때는 원래 훑기를 그대로 돈다.
3. **`_ordered` 반복 계산 줄이기** (`router.py:248`)
   - `lanes = _lanes(bb, led)` 를 함수 앞에서 한 번. 안쪽은 `for X in lanes + [A[0], B[0]]`. `cands` 에
     넣는 순서·원소는 같다(`_lanes` 는 `bb`·`led` 만으로 정해진다, `router.py:66`).
   - `_coster.cost` 는 `over` 를 끝까지 합한 뒤, 0 이 아니면 `return over, 0`. 필터 `s[0][0] == 0` 이 그런
     후보를 버리므로 `c` 는 안 쓰인다(`router.py:272`).
   - 정렬 키 `(s[0][1], s[1])`, `set(map(tuple, cands))`, 필터는 손대지 않는다.

## 검증

- 새 시험 `tests/test_breadboard_route.py::PrefilterSame` — 시험 안에 원래 `_on_seg`·`_seg_in_box` 본문을
  대조용으로 복사해 두고, 고정 시드 난수 구간과 경계 사례(수직 거리 1.49/1.5/1.51/2, 상자 변과 일치·±ulp,
  0.1 배수 좌표, 1px 미만 구간, 대각선, margin 0·6)에서 엔진과 답이 같은지 본다. 공용 사본을 읽기만 한다.
- 일회성 pickle(`tmp/route-speed/`): e4 `_mux_paths(None/0.0)`·`_dmux_paths(None/0.0)`, e5
  `place_paths(BCD, LAYOUT, None/0.0)`. 계산마다 새 엔진 사본에서 뜨고 시간도 잰다.
- 측정: 같은 워크트리에서 기준점과 고친 뒤를 전체 스위트 3회씩. 그룹 합산은 junit 에서.

## 예상 (측정 전)

선검사는 함수 호출 비용(1774만 회)을 없애지 못한다. `_valid` 쪽은 절반 남짓, `_ordered` 쪽은 덮는
후보 비율만큼 준다. 합쳐 1.5~2배 — 그룹 단독 57초 → 30~38초, 전체 104초 → 75~85초.
