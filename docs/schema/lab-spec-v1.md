# lab-spec/v1 — 실험 명세 스키마

Task 1 에서 실험1(truth-table)·실험10(capture + stepped)·실험6(심볼릭 토큰)
세 건으로 시험해 확정했다. `scripts/lab/spec_parser.py` 가 이 계약을 구현한다.

실물 3종이 이 문서의 적합성 픽스처다 — 별도의 합성 픽스처를 만들지 않는다.

- `실험01/체크리스트/명세.md` — truth-table 5개, 다중 출력 표 포함
- `실험06/체크리스트/명세.md` — 심볼릭·복합 토큰, `2^n` 아닌 행 수
- `실험10/체크리스트/명세.md` — `capture` 와 `stepped` 가 한 문서 안에 공존

## 문서 프론트매터

`---` 로 감싼 블록. **PyYAML 에 의존하지 않는다** — 파서는 아래 형태만 읽으면 된다
(플로우 스타일 리스트 `[a, b]`, 플로우 스타일 맵 `{k: v}`, 2칸 들여쓰기 블록 리스트).

| 필드 | 필수 | 값 |
|---|---|---|
| `schema` | ● | `lab-spec/v1` 고정 |
| `week` | ● | 정수 |
| `experiment` | ● | 정수 |
| `title` | ● | 문자열 |
| `source_manual` | ● | 교안 PDF 경로 (저장소 루트 기준 상대경로) |
| `power` | ● | 전원 레일 이름 → 전압 문자열의 **열린 맵**. 회로가 실제로 쓰는 레일을 전부 싣는다 (예: `{VCC: "+5V", GND: "GND"}`, `{VCC: "+5V", V15: "+15V", GND: "GND"}`). 레일 이름에 고정 enum 은 없다 |
| `items` | ● | 항목 리스트 |

### `power` — 레일이 여러 개인 회로 (세 번째 파손)

Task 1 리뷰에서 발견된 세 번째 스키마 파손이다(첫 번째는 아래 "`source` — 다중 출력
표의 표기", 두 번째는 "`stepped` 의 `encoding` 적용 범위"). 실험10 은 로직단 +5V 말고
`741` OP amp 구동에 **+15V 레일을 따로 쓴다**(pin 7 → +15V, pin 4 → GND — p7·p15
회로도, vision 확인. R9/R10/R11·R13 분압기는 이 +15V 레일에서 pin 3(+) 로 들어가는
기준전압 배선이지 별도의 음전원이 아니다). `power` 를 `{VCC, GND}` 고정 키 2개로
규정하면 이 레일을 프론트매터에 실을 자리가 없어서, "OP amp 는 +15V 를 쓴다" 같은
요구가 항목 산문에만 남고 프론트매터만 읽는 소비자(예: 결선도 자동 생성기)에게는
보이지 않는다.

**고침(v1 범위 안):** `power` 를 고정 키 맵이 아니라 **레일 이름 → 전압 문자열의
열린 맵**으로 재정의한다. `실험10/체크리스트/명세.md` 는
`{VCC: "+5V", V15: "+15V", GND: "GND"}` 로 세 레일을 전부 싣는다.

## 항목 (`items[]`)

| 필드 | 필수 | 값 |
|---|---|---|
| `id` | ● | `E<실험>.P<항목>` (예: `E1.P1-1`, `E6.P3`) |
| `title` | ● | 문자열 |
| `device` | ● | `LED` \| `7segment` \| `oscilloscope` \| `DMM` (복수 가능) |
| `ics` | ● | IC 이름 리스트. **준비물 페이지의 표기를 따르되, 항목이 실제로 쓰는 패키지만 싣는다.** 패키지 단위이지 게이트 단위가 아니다 |
| `tables` | ● | 이 항목이 쓰는 표 ID 리스트 (`[T1, T2]`) |

`ics` 는 **패키지 수**를 센다. 회로도에 `74HC08` 라벨이 두 번 나와도 쿼드 패키지에서
게이트 2개를 뽑는 것이므로 `["74HC08"]` 이다 (실험1 p11 이 근거). `×2` 같은 수량
접미사를 쓰지 않는다. 준비물 페이지에 있어도 그 항목이 안 쓰면 넣지 않는다 —
실험1 준비물엔 `74HC86` 이 있지만 어느 항목도 XOR 회로를 구성하지 않으므로
`ics` 어디에도 넣지 않는다(예비용 또는 다른 연도 잔재로 판단).

본문에 흔히 나오는 `# <id> · <제목>` 최상위 헤딩(예: `# E1.P1-1 · 3-input AND / OR
gate 구성`)은 **순수 장식이다 — 계약에 없다.** 항목과 표의 결합은 오직 프론트매터
`items[].tables` 리스트로만 이뤄지고, 표가 본문에서 어느 `#` 섹션 아래 물리적으로
있는지는 파서가 참조하지 않는다. 계약 대상 헤딩은 `## T<n> · 제목` 뿐이다.

## 표 (`## T<n> · 제목` 아래 속성 리스트)

표 헤딩은 `## T<n> · <제목>` 형태이고 **`T<n>` ID 는 문서 전체에서 유일**하다.
항목이 여러 개여도 **ID 는 유일하기만 하면 되고, 본문 등장 순서와 일치할 필요는
없다** (`실험01/체크리스트/명세.md` 의 헤딩 순서는 T1, T2, T6, T7, T3, T4, T8, T9,
T5 다 — T1~T5 재번호 금지 지시의 결과다). `items[].tables` 가 가리키는 ID 는
본문 헤딩과 정확히 일치해야 한다 (누락도 고아도 오류다).

| 필드 | 필수 | 값 |
|---|---|---|
| `kind` | ● | `truth-table` \| `stepped` \| `capture` — **표 단위 속성이다** (실험10 이 근거) |
| `encoding` | `capture` 외 ● | `0/1` \| `H/L` — **표의 속성이다. 서로 변환하지 말 것** |
| `source` | ● | `manual:p11` \| `derived (Y = A·B·C)` \| `past-report:2020` |
| `expected` | `capture` 만 | 정성 서술 산문. 셀 표가 없는 표의 예상값이 여기 들어간다 |
| `role` | 선택 | `record` \| `reference` — 생략하면 `record`이며, `source` 만으로는 가를 수 없는 참조표(`reference`)와 기록 대상(`record`)을 구분하기 위한 필드다 |

`capture` 를 뺀 모든 표는 속성 리스트 뒤에 마크다운 표가 하나 온다.

### 여러 줄 값 — 들여쓴 연속 줄 이어붙이기

`expected` 처럼 값이 길어지면 다음 줄로 넘어간다. **원 줄 다음에 오는 줄이 최소 2칸
들여쓰기로 시작하면 앞 속성 값의 연속으로 보고, 줄바꿈을 공백 한 칸으로 바꿔 이어
붙인다.** 들여쓰기가 2칸 미만이거나, 다음 `- key:` 줄, 빈 줄, `#`/`##` 헤딩이 나오면
값이 끝난 것으로 본다. 실물 픽스처: `실험10/체크리스트/명세.md` 의 T1 `expected` 가
5줄이다 — 이 규칙 없이는 파서가 이 픽스처를 못 읽는다.

### `kind` 가 표 단위인 이유

실험10 하나가 둘로 갈린다. 교안 p11 은 "파형을 그려라"(정성) 이고 p16 은
"전이점을 기록하고 출력 전압을 측정"(스텝별 셀) 이다. 같은 실험 안에서
`T1: capture`, `T2: stepped` 다. `kind` 를 실험 속성으로 두면 이 문서를 못 쓴다.

### `source` — 다중 출력 표의 표기

출력이 여러 개인 표는 `derived (...)` 안에 **`;` 로 식을 나열**한다. 출력 열 이름이
왼쪽에 온다. 실험1 T5 가 실물이다.

```
- source: derived (X = A + (A'·B)' ; Y = A + B ; Z = (A'·B)')
```

Task 6 의 역검산기는 `;` 로 쪼갠 뒤 각 식을 해당 출력 열에 대해 검산한다.

### `stepped` 의 `encoding` 적용 범위

`stepped` 표는 스텝 라벨·조작 서술·실측 전압·로직 비트가 한 표에 섞인다
(실험10 T2 의 `3번 핀 전압` 열과 `7405 핀8` 열). 따라서:

- `encoding` 은 **선언은 하되 셀 알파벳 검사를 하지 않는다.** 로직 값 열에만 의미가 있다
- 행 수 `2^n` 검사를 하지 않는다. 스텝 축은 입력 조합이 아니다

### `role` — 참조표와 기록 대상 구분 (네 번째 파손)

Task 1 리뷰에서 발견된 네 번째 스키마 파손이다(첫 번째는 위 "`source` — 다중 출력
표의 표기", 두 번째는 위 "`stepped` 의 `encoding` 적용 범위", 세 번째는 위 "`power`
— 레일이 여러 개인 회로"). `실험01/체크리스트/명세.md` 의 `T6`~`T9` 는 교안 2입력
이론표를 원문 그대로 옮긴 참조표다 — 학생이 배선하지도, 실험실에서 채우지도
않는다. 그런데 `items[].tables` 에 다른 진짜 기록 대상 표와 똑같이 얹혀 있어서,
`items[].tables` 를 순회해 기록 템플릿과 확인 칸을 만드는 소비자 입장에서는
"모든 표는 실험실에서 채우는 기록 대상"이라는 암묵적 가정이 깨진다. `source` 로는
이 둘을 구분할 수 없다 — `실험06/체크리스트/명세.md` 의 표 5개도 전부
`source: manual:pN` 이지만 그건 진짜 기록 대상이다.

**고침(v1 범위 안):** 표 속성에 **`role`**(`record` 기본값 | `reference`)을
추가한다. `실험01/체크리스트/명세.md` 의 `T6`·`T7`·`T8`·`T9` 에 `role: reference`
를 붙인다.

### 검사 강도

| 검사 | 대상 | 강도 |
|---|---|---|
| `items[].tables` ↔ 본문 헤딩 일치 | 전부 | error |
| `kind` 가 세 값 중 하나 | 전부 | error |
| `role` 이 `record`/`reference` 중 하나 | 전부 | error |
| `capture` 가 아닌 표에 `encoding` 부재 또는 `0/1`·`H/L` 밖의 값 | 전부 | error |
| `capture` 표에 `expected` 부재 | `capture` | error |
| `capture` 표에 셀 표(마크다운 표) 존재 | `capture` | error (파서가 던진다) |
| `capture` 가 아닌 표에 셀 표(마크다운 표) 부재 | 전부 | error (파서가 던진다) |
| 행의 셀 수가 헤더 열 수와 다르다 | 전부 | error |
| 셀에 escape 된 파이프(`\|`)·`<br>` 태그·탭 문자 | 전부 | error |
| 행 수 = `2^n` | `truth-table` | **warn**, 그리고 `X` 가 있는 표에서는 건너뛴다 |
| 출력 비트 ↔ `source` 부울식 역검산 | `derived (...)` 이고 rows 가 있는 표(`kind` 를 안 본다 — `stepped` 도 검산한다) | error |
| `source` 부재 | 전부 | error |
| 한 표 안에 같은 이름의 열이 둘 | 전부 | error (파서가 던진다) |
| 방향을 붙인 진단 문장 | 전부 | info (판정하지 않고 센다) |

행 수 검사가 warn 인 이유: 실험6 R-S Latch 는 3입력인데 5행이다 (`x x 0` 이 4개 조합을
한 줄로 접는다). 이것은 오류가 아니라 교안의 정상 표기다.

이 표는 코드를 손으로 옮겨 적은 요약이고, 정본은 코드다 — 다만 열네 줄이
한 함수에 있지 않다. `kind` 값·`capture` 표의 셀 표 유무·열 이름 중복은
`spec_parser.py` 의 `_parse_table`(파서이므로 예외로 던진다)이 맡는다.
`role`·`encoding`·`capture` 의 `expected`·`source` 부재는
`validate.py` 의 `check_metadata`, 행 수 `2^n` 은 같은 파일의
`check_row_count`, 출력 비트 역검산은 `check_boolean`이 맡는다. 셀 수
불일치·escape 된 파이프·`<br>` 태그·탭 문자는 같은 파일의
`check_table_integrity`(전부 error)가 맡고, 방향을 붙인 진단 문장은
`check_diagnostic_claims`(info — 판정하지 않고 센다)가 맡는다.
`items[].tables` ↔ 본문 헤딩 일치 한 줄만은 이 목록에서도 예외라 두 파일에
걸친다 — 항목이 없는 표를 가리키면 `spec_parser.parse_spec`이 파싱 단계에서
막고, 반대로 어느 항목도 가리키지 않는 고아 표는 `validate.py` 의
`check_orphan_tables`가 검증 단계에서 잡는다. 요컨대 정본은
`spec_parser.py`(`parse_spec`·`_parse_table`)와 `validate.py`(`check_table_integrity`·
`check_metadata`·`check_row_count`·`check_boolean`·`check_orphan_tables`·
`check_diagnostic_claims`)를 합친 것이다.

위 표는 네 줄이 코드와 반대로 적혀 있었다. 그중 둘(`encoding`·`expected`)은
`존재`/`부재`가 그대로 뒤집혀 있었고, 나머지 둘(셀 표 유무를 다루는 두 줄)은
`존재`/`부재` 문구는 맞았지만 대상(`전부` ↔ `capture`)이 서로 뒤바뀌어
있었다. 게다가 실재하지 않는 검사 한 줄까지 섞여 있었다 — 문서만 읽고는
드러나지 않다가 격리 재생성(실험06·실험10)이 코드를 실측해서야 드러났다.
이 표와 코드의 실제 동작이 어긋나면 코드가 옳고 이 표가 틀린 것이다 —
문서만 읽고 저작하면 파서조차 못 읽는 명세를 쓰게 된다.

## 셀 값 — 닫힌 enum 이 아니라 열린 토큰 (R3)

실증된 토큰:

```
0 1                       비트 (encoding: 0/1)
L H                       비트 (encoding: H/L)
X                         don't care
0->1  1->0                엣지
Q(t-1)  Q(t-1)'           이전 상태 / 그 보수
0 : Reset  1 : Set        비트 + 라벨 복합
Q(t-1)' : Toggle          보수 + 라벨 복합
Q=D  Q0  Z                메모리 상태 / Hi-Z
D0 D1 D2 D3               신호 이름
```

`0 : Reset` 같은 복합 토큰은 닫힌 enum 으로 담기지 않는다. 콜론은 표 파싱을 깨지
않는다 — 셀 구분자는 `|` 다.

**정규화는 이것만:** `x`→`X`, `-`→`X`, don't-care 열의 빈칸→`X`, 앞뒤 공백 정리.
**`H/L` ↔ `0/1` 변환 금지.**

명세 파일에는 **교안 원문 그대로** 적는다(교안이 소문자 `x` 를 쓰면 `x` 로 적는다).
정규화는 파서가 한다 — 그래야 정규화 규칙이 픽스처로 실제 검증된다.

## 표기 (R5·R6) — 적용 범위가 핵심이다

- **보수:** 저작은 `'` 를 쓰고 **괄호로 스코프를 명시**한다. `(A·B)'` 는 `A·B` 위에,
  `A'` 는 `A` 위에 바가 온다. PDF 렌더 시 **부울식만** 오버바로 승격한다.
- **오버바 승격을 하지 않는 곳:** 표 헤더, 신호명, **그리고 셀 값.**
  실험6 의 `Q(t-1)'` 은 상태 토큰이지 부울식이 아니다. 이 구분을 어기면
  진리표 셀이 렌더링에서 망가진다.
- 교안 PDF 가 타이포그래피 어포스트로피(`’`)를 쓰더라도 저작은 ASCII `'` 로 적는다.
- **active-low:** 맨 이름을 쓰고 **첫 등장에만 `(Active Low)`** 를 붙인다.
  실험9 만 교안 표기(`GWN`/`GRN`)를 그대로 쓴다.
- XOR 는 `⊕`, don't care 는 `X`.

## 교안 판독 규칙

`extract_text()` 는 오버바·라이징 엣지 화살표·아래첨자를 파괴한다. 회로도는 아예
래스터 이미지라 벡터 좌표도 안 나온다 (실험1 p13 확인). 따라서:

- **회로도와 기호는 반드시 vision 으로 판독한다.** 필요하면 `pdftoppm -r 250~300` 으로
  렌더한 뒤 관심 영역을 크롭·확대해서 본다
- 판독 결과가 텍스트 추출과 어긋나면 **vision 이 이긴다**
- 확정하지 못한 배선은 추측으로 채우지 말고 `source` 에 미확정임을 적고 미확정 표에 올린다
- **지뢰:** 실험6 교안 p9·p11 의 `C` 열은 `extract_text()` 를 돌리면 **리터럴 `1`** 이
  나온다(`0 1 0` / `1 1 1` / `... 1 Q(t-1)` 식으로). 실제로는 라이징 엣지 글리프인데,
  그 자리에 살아 있는 텍스트(`1`) 위로 불투명 이미지가 겹쳐 그려져 있어서다. 텍스트
  추출 결과를 "정답"으로 믿고 표를 검증하면 레벨 `1` 과 라이징 엣지를 구분하지 못해
  T3·T5 를 **자신 있게** 틀리게 고치게 된다 — vision 판독값(`0->1`)만 신뢰한다

## 교안에서 오지 않은 문장 — 명세에서 가장 위험한 자리

교안에서 옮긴 값은 대조할 원본이 있다. 그런데 명세 산문에는 원본이 없는 문장이
섞인다 — 명세를 쓴 사람이 회로를 보고 **추론해서** 넣은 것이다. 이 문장들은
아무도 대조하지 않은 채 보고서로 그대로 옮겨 간다.

**가장 위험한 형태는 진단 문장이다:** "~하면 ~를 의심한다", "~보다 크게 나오면
~다" 처럼 **관측 결과에 방향을 붙이는** 문장. 방향이 거꾸로여도 문법·서식 검사는
전부 통과하고, 읽는 사람에게는 오히려 친절해 보인다.

- **지뢰:** 실험02 명세에서 이 형태로 **두 번** 틀렸다. (1) `Rp` 배선 순서를
  잘못하면 `Rp` 가 "터무니없이 크게" 나온다고 적었는데, 절차대로 계산하면 분자가
  0 에 묶여 **0 에 가깝게** 나온다. (2) 전파지연이 데이터시트 typ 보다 "작게"
  나오면 단 수를 의심하라고 적었는데, 규격 조건(`C_L = 50pF`·`VCC 4.5V`)과 실제
  회로가 달라 **작게 나오는 쪽이 정상**이다. 게다가 단 수 후보가 둘뿐이라, 그
  진단을 따르면 값이 정확히 2배가 되면서 **틀린 답이 규격에 더 가까워 보인다.**
- **쓰기 전에 절차 자신의 산술로 한 번 굴려 본다.** 그 상태의 각 스텝에 실제로
  어떤 값이 들어가는지 대입해 부호와 크기를 확인한다. 굴려 볼 수 없으면 방향을
  단정하지 말고 **무엇을 보고 판정할지**만 적는다(예: "단 수는 결과가 아니라
  브레드보드의 점퍼를 세어 확인한다").
- 진단 문장은 `source` 에 교안 쪽을 달 수 없다. 달 곳이 없다는 것 자체가
  **대조되지 않은 문장이라는 표시**다.

## v1 에 없는 것 (의도적)

- `value_type` — `kind` 와 토큰 집합으로 흡수됐다
- `numeric` / `DMM` kind — 전 코퍼스 실측 수치가 2개뿐이라 폐기 (스펙 §개정 근거)
- 신뢰도 필드 — `source` 하나로 충분하다
- 열 단위 `encoding` — `stepped` 에서만 필요한데, 알파벳 검사를 끄는 것으로 충분하다
- FPGA(13~15주차·텀프로젝트) — 산출물이 HDL·시뮬레이션 파형·핀 할당이라
  이 스키마로 확장하지 말고 별개 파이프라인으로 설계한다
