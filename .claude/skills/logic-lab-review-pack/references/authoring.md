# 기초부터 이해하는 설명

학생은 논리회로를 오래전에 배웠고 보고서는 주로 AI로 작성한다. 용어·기호를 알고 있다고 가정하지 않는다.
생명과학 정리노트의 토스 말투를 따른다. 본문·제목·요약·힌트·캡션은 짧고 다정한 ‘~해요’체로 쓴다. ‘보낸다’ 대신 ‘보내요’, ‘무관하다’ 대신 ‘영향을 주지 않아요’처럼 구체적인 동사를 사용한다. 정확한 설명에서는 정의·조건·입력·출력·인과를 빠뜨리지 않는다. 수식, 신호 이름, 원문 직접 인용은 바꾸지 않는다.
각 팩은 필요한 기초를 자체 포함한다. 짧은 전체 요약 → 동기 → 필요한 기초 → 동작 원리 → 완성 예제 → 실험 항목별 조작·관찰·이유 → 일부 단계 연습 → 기출 순서.
비유 뒤에는 실제 신호와 대응시킨다. 식의 기호를 정의하고 진리표 한 행을 읽는 법부터 보여준다.
완성된 진리표·타이밍도와 도출 과정을 제공한다. 풀이를 숨길 수 있지만 강제 학습 잠금이나 서술형 자동 채점은 하지 않는다.
초기 상태 미지정이면 미정이라고 설명한다. don't-care는 알 수 없는 값과 다르다.
수행하지 않는 과거 실험 내용은 보충으로 표시한다. 실제 측정 수치는 기록 없이는 만들지 않는다.

## 첫 토픽: 회로를 쓰는 이유

`t-start`의 제목은 ‘왜 이 회로를 쓰는지 먼저 알아봐요’로 쓴다. 앞부분의 새 동기 설명은 약 2~4개 짧은 문단으로 아래 흐름을 연결한다. 기존 수행 범위·판본·예상과 측정 구분은 이어서 보존한다.

1. 해결할 문제: 무엇을 판단·계산·선택·변환하려는 상황인지 먼저 보여 준다.
2. 회로가 필요한 이유: 단순한 연결이나 기존 방식에서 어려운 점과, 이 회로가 해결하는 일을 설명한다.
3. 작은 입력·출력 예: 신호 이름과 0·1의 의미를 설명하고 실제 값 한 가지를 따라간다. 조건·극성·초기 상태가 필요한 경우 생략하지 않는다.
4. 이번 실험과 연결: 무엇을 바꾸고 관찰하면 그 역할을 확인할 수 있는지 설명한다.

정의, 핀 암기, ‘시험에 나와요’만으로 동기를 대신하지 않는다. 활용 사례를 교안의 주장으로 꾸미지 않는다. 직접 구성한 상황은 ‘이해를 위한 예시’, 교안 밖 원리는 ‘보충’으로 표시한다. 이상적인 모델의 예와 실제 IC의 극성을 구분하고 실제 측정값을 만들지 않는다. 비유는 실제 신호에 대응시킨다. 상세 식과 진리표는 뒤의 개념 토픽에 둔다. 첫 토픽의 `div.sum`에도 해결하는 문제를 포함한다.

## 생명과학과 동일한 화면
assets/note-template.html, review-template.html은 생명과학 원본을 그대로 유지한다. CSS·색·레이아웃·패널·페이지 이동을 새로 디자인하지 않는다.
토픽은 조립기가 article.topic/h3로 감싼다. fragment 안에는 아래 순서의 layer를 사용한다.
eli5(직관) → formal(정확한 원리·조건) → warn(혼동 방지) → supp(보충, 필요할 때).
각 layer는 div.layer + span.layer-title로 표시한다. 교수 발언 자료가 없으면 prof를 만들지 않는다.
토픽 마지막에 직계 자식 div.sum[hidden]을 두고 본문에 나온 핵심 1~3개만 적는다. 이 내용이 우측 요약 패널로 이동한다.
새 manifest에는 note_presentation_version=2를 지정한다. fragment에 ‘이 개념으로 풀 문제’, 출처 문구·sources 요소를 넣지 않는다. topics[].sources와 included 문제의 topics로 해당 토픽 MD 끝에 출처·문제 링크를 자동 생성한다. 원자료 쪽수·판본 파일명·재제작 대조 기록 등 추가 근거는 topics[].md_notes에 쓴다. 개념 이해에 필요한 불확실성·극성·실험 수행 범위 경고는 HTML 본문에도 남긴다.
설명 그림은 직접 SVG로 다시 그린다. 원문 스캔, 낡은 그림의 확대/덧칠, evidence 이미지를 설명용으로 재사용하지 않는다. 신호 방향·반전 bubble·접속점·비접속 교차·비트 순서·enable 극성을 원문 및 식/진리표와 대조한다. 원문과 도출값 충돌이 있으면 이상 모델임을 설명하고 대조 기록은 MD에 남긴다. 모든 SVG에 viewBox/title을 넣고 외부 이미지 없이 제작한다. 글자는 최소 18px, 선·라벨은 양쪽 테마에서 읽혀야 한다. HTML과 MD는 같은 SVG를 참조한다. 진리표는 텍스트 표로 작성한다.
이미지는 div.figure 또는 figure.figure로 감싼다. 원본 템플릿은 .figure 안의 이미지에만 너비 제한을 적용하므로, 원문·풀이 details 안의 이미지도 같은 규칙을 따른다. 모바일과 인쇄에서 그림의 오른쪽이 잘리지 않는지 확인한다.
표시 버전 없는 기존 기출 fragment는 div.problem, details.original, details.hint, details.solution 순서다. 새 review_presentation_version=2는 [문제지·해설지 작성 계약](workbook.md)의 문항 JSON을 사용한다. 문제에 주어진 그림과 완성 회로를 각각 questions/solutions로 저장하고 텍스트 표·수식을 유지한다.
문제·출처 → 필요한 개념 링크 → 힌트 → 단계별 풀이 → 최종 답 → 검산 → 흔한 실수를 모두 제공한다.
카드 제목은 조립기가 article.card/h3로 붙인다. 번호가 정답 검증 상태를 대신하지 않는다.
객관식 원문이 아니면 객관식으로 바꾸지 않는다. 진리표·부울식·설계·타이밍·계산·서술형을 유지한다.
HTML은 KaTeX용 $...$/$$...$$ 또는 data-tex를 가진 MathML을 지원한다. 형식별 의미가 같아야 한다.
같은 식의 동치 표현과 다른 유효 설계도 인정한다.

위젯은 이해에 필요한 경우에만 넣고 같은 내용을 static-equivalent에 표·그림·설명으로 남긴다.
기본 mux2 위젯에는 S select, I0/I1 checkbox, output을 넣고 각 input을 label로 설명한다.
MD는 위젯 조작부를 제외하고 정적 자료·힌트·풀이를 모두 펼쳐서 제공한다.

## 문제설명 저작

문제설명은 원문/조건/구할 것/주어진 그림을 문제지 payload에서 자동으로 가져온다. 추가 조각은 article/h1 없이 작성한다. 아래 data-explanation 영역을 순서대로 하나씩 포함한다.

- recall(eli5): 제목 `이 문제를 보면 떠올려요`. 문제 속 단서를 보면 떠올릴 것을 `p.lead.cue` 구절 1개(자식 태그 없는 60자 이내 명사형, inline `$…$`만, `$$` 금지)와, 단서→떠올릴 것→이유를 담은 `<p>` 문단으로 쓴다. 조각의 첫 영역이다. 구절은 그 문항 풀이의 실제 첫 판단과 맞아야 하고, 원문 밖 조건을 끌어오거나 disputed·unresolved 답을 단정하지 않는다.
- understand(eli5): 무엇을 하는 문제인지, 기호의 뜻과 쉬운 직관.
- start(formal): 실제 첫 줄 또는 첫 행을 작은 입력 예로 보여주고 {{NOTE_HREF}}#토픽ID로 개념 연결.
- solve(formal): 모든 소문항의 단계별 판단 이유와 완성 표·식·회로.
- verify(formal): 최종 답과 독립 계산/검산 방법. 단순히 “검산한다”라고만 쓰지 않는다.
- pitfall(warn): 해당 문항의 실수와 이유. disputed는 “답안 충돌”, unresolved는 “정답 미확정” 경고와 적용 조건 필수.
- retry(formal): 설명을 닫고 재현할 순서 1~3개의 li.

직계 div.sum[hidden]에 시작 방법·핵심 판단·검산을 담는다. 첫 줄은 `<p><strong>떠올릴 것:</strong> 구절</p>`이다. 본문 풀이를 details나 hidden으로 접지 않는다. 조각은 problem-explanations/<id>.html, 새 설명 그림은 problem-explanations/figures/<name>.svg에 저장한다. 그림은 직접 제작하고 viewBox/title, 최소 18px 라벨, 두 테마의 대비를 확인한다. 기존 직접 제작 SVG를 재사용해도 된다. 발행 문서의 그림 경로는 .pack/problem-explanations/figures/.. 또는 기존 .pack/figures/..이다. 표는 table-wrap 텍스트 표로 쓴다.

독립된 식은 설명 문장과 문단을 분리한다. 문제설명 렌더러는 식만 있는 `<p>`(일반 부울식 또는 `$...$`/`$$...$$`/LaTeX display 문단)를 수식 카드로 자동 감싼다. 원문 식 번호와 내용은 그대로 보존하며, 감지되지 않는 독립 수식은 `<div class="equation-card" role="group" aria-label="수식">` 안에 명시한다. 카드 안에는 식을 넣고 해석·조건·주의 문장은 밖에 둔다.

문제설명의 표도 본문과 분리된 `table-card`로 표시한다. 렌더러가 문제 읽기와 설명 조각의 표를 자동으로 감싸며 기존 `table-wrap`/`work-table`, 표 머리·주어진 값·빈칸·병합 셀은 그대로 유지한다. 명시적으로 저작한 table-card는 중첩하지 않는다. 표에 대한 해석이나 주의 문장은 카드 밖에 둔다.


### 문제설명 표 배치

`problem-explanations/table-layout.json`(version=1)에 모든 표를 `<문항ID>/<original|conditions|ask|explanation>/<0부터 순번>` key로 기록한다. expected_headers는 원래 최하위 열 머리글, columns는 role(index/control/input/intermediate/output/description), kind(signal/bus/expression/text/connector/index), 한국어 group 및 선택적 min_rem이다. 이름으로 역할을 추측하지 않는다. boundaries는 left(왼쪽 열의 0부터 번호)와 kind(major/minor)로 명시한다.

signal은 같은 표에서 같은 폭(하한 3rem), bus/수식은 내용 기반으로 줄바꿈 없이, text는 가용 폭을 공유한다. 경계 여백은 major 양쪽 0.5rem씩, minor 양쪽 0.25rem씩 기본 여백에 더한다. 짧은 표는 필요한 폭만 쓴다. 같은 열 구성의 빈 표·완성 표는 같은 pair를 지정하여 너비를 공유한다. 열 구성이 다르면 pair를 지정하지 않는다. 겹치는 병합 셀·머리글 불일치는 빌드 오류다. 그룹 머리글은 생성기가 추가하고 MD에는 원래 행만 내보낸다.

기존 팩은 explain-stage의 `--sync-explanation-template`으로 표시된 문제설명 CSS 블록만 동기화한다. 관리 대상 표의 첫 열 최소 폭은 해제하며 모바일 가로 스크롤은 table-card 한 곳만 사용한다. 글자 축소·열 숨김·간격용 빈 열은 금지한다. JSON 없는 legacy 입력은 종전 표를 보존한다.
