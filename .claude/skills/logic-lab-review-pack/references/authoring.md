# 기초부터 이해하는 설명

학생은 논리회로를 오래전에 배웠고 보고서는 주로 AI로 작성한다. 용어·기호를 알고 있다고 가정하지 않는다.
생명과학 정리노트의 토스 말투를 따른다. 본문·제목·요약·힌트·캡션은 짧고 다정한 ‘~해요’체로 쓴다. ‘보낸다’ 대신 ‘보내요’, ‘무관하다’ 대신 ‘영향을 주지 않아요’처럼 구체적인 동사를 사용한다. 정확한 설명에서는 정의·조건·입력·출력·인과를 빠뜨리지 않는다. 수식, 신호 이름, 원문 직접 인용은 바꾸지 않는다.
각 팩은 필요한 기초를 자체 포함한다. 짧은 전체 요약 → 동기 → 필요한 기초 → 동작 원리 → 완성 예제 → 실험 항목별 조작·관찰·이유 → 일부 단계 연습 → 기출 순서.
비유 뒤에는 실제 신호와 대응시킨다. 식의 기호를 정의하고 진리표 한 행을 읽는 법부터 보여준다.
완성된 진리표·타이밍도와 도출 과정을 제공한다. 풀이를 숨길 수 있지만 강제 학습 잠금이나 서술형 자동 채점은 하지 않는다.
초기 상태 미지정이면 미정이라고 설명한다. don't-care는 알 수 없는 값과 다르다.
수행하지 않는 과거 실험 내용은 보충으로 표시한다. 실제 측정 수치는 기록 없이는 만들지 않는다.

## 개념 토픽 안의 순서: 결론 먼저 (읽기 방식 v1)

위의 팩 전체 순서는 토픽을 어떻게 늘어놓을지 정한다. 이 절은 회로·소자 하나를 설명하는 **토픽 안**의 순서를 정한다. 레이어 순서(eli5 → formal → warn → supp)는 그대로 지킨다. 한 토픽에는 새 동작 원리를 하나만 둔다. 새 팩과 전체 갱신에는 manifest.note_reading_version=1 을 지정한다. build 가 아래 표시한 [검사] 항목을 거절한다(`scripts/lab/review_pack/note_reading.py`).

목표는 텍스트를 줄이는 것이 아니라 어느 문장이 핵심인지 글이 대신 알려 주는 것이다. 문장마다 무게가 같고 같은 사실이 한 쪽에 서너 번 나오면 학생은 핵심을 스스로 가려야 한다.

1. 결론부터: eli5 첫 레이어의 제목은 이 토픽의 결론이나 결론을 묻는 질문으로 쓴다(‘S′=R′=1이면 Q는 얼마일까요?’, ‘칸 A에 1을 쓰려면 IN0=1, WR1=1, WR0=0이에요’). 제목 바로 다음 문단은 `<p class="gist">` 이고, 그 첫 문장을 `<strong>` 으로 감싼 답·결론으로 쓴다. 질문형 제목의 답은 접지 않고 바로 보인다. [검사]
2. 제목은 내용을 말한다: 모든 레이어 제목은 그 레이어가 알려 주는 사실을 한 문장으로 쓴다(‘0이 들어간 쪽 출력이 먼저 1로 정해져요’, ‘00은 주지 않아요: Q와 Q′가 둘 다 1이 돼요’). ‘새 이름부터 알아봐요’·‘한눈에 보기’·‘작은 예부터 살펴봐요’·‘조건과 작동 원리를 확인해요’·‘헷갈리기 쉬운 것/말’ 같은 절차 제목은 쓰지 않는다. 연습 레이어 ‘한 단계만 풀어 봐요’는 그대로 둔다. [검사]
3. 새 용어 소개: 결론 다음에 필요한 핀·신호·용어만 짧게 소개한다. 신호가 셋 이상이면 문단 대신 `신호 | 들어가는 곳 | 하는 일` 같은 표로 쓴다. 새 용어는 쓰기 전에 소개한다.
4. 규칙표를 본문에 두지 않는다: 조건|결과 「한눈에 보기」 표는 쓰지 않는다. 규칙은 우측 요약 패널(div.sum 의 외울 규칙)과 추적표의 동작 열이 맡는다. ‘다섯 줄로 기억하면 충분해요’, ‘아래 표는 외울 필요 없고’ 같은 군말 문장도 쓰지 않는다. [검사] 앞 회로와의 대응표(새 입력 | 앞 회로 입력 자리 | 결과)는 원리를 보여 주므로 formal 에 둘 수 있다.
5. 원리: formal layer. 새 회로를 ‘앞단 + 이미 아는 회로’로 나눌 수 있으면 앞단 식만 대입하고 아는 규칙으로 돌아간다. 나눌 수 없으면 핀 동작 표로 쓴다.
6. 추적표에 이유를 넣는다: 입력을 차례로 바꾸는 추적표의 마지막 열은 ‘왜 이 값인가요’(또는 ‘동작 · 이유’)로 두고, 각 행이 그 값이 된 이유를 짧게 적는다. 열 코드는 `t`(설명 글)다. 표 아래에 따로 늘어놓던 행별 설명은 이 열로 옮긴다. 표의 값은 직접 검산한다.
7. 비교 행 표시: 같은 입력인데 결과가 다른 두 행처럼 비교할 행에는 `<tr data-row="compare">` 를, 금지·위험 입력 행에는 `<tr data-row="avoid">` 를 붙인다. 템플릿이 비교 행을 색칠하고 굵게 하며, MD 는 굵은 글씨로 옮긴다. 비교 행은 한 표에 두 개 이상이다. [검사] 표 뒤에는 ‘색칠한 ②와 ④는 입력이 같고 Q만 달라요’처럼 무엇이 갈렸는지 한 문장만 쓴다.
8. 대비 개념(레벨과 엣지처럼): 같은 입력열을 두 소자에 나란히 넣은 시간표를 formal 에 둔다.
9. warn: 제목에 결론을 쓴다(‘핀 번호는 결선도 표로 다시 확인해요’). 이름이나 모양이 비슷해 헷갈리는 핀·용어, 실험 주의점, 교안 자체의 오류(식과 그림이 어긋남 등)를 둔다.
10. supp: 한 단계 연습.
11. 출처는 본문에 두지 않는다: ‘교안 목표 1’·‘교안 p7’ 같은 출처 표식이나 ‘교안 p7도 …라고 해요’ 같은 근거 문장은 쓰지 않고 topics[].sources·md_notes 에 남긴다. 교안 자체의 오류를 다루는 warn 문장 안의 쪽수는 내용이므로 쓴다. 보고서 범위·판본·예상값 고지는 div.sum 의 헷갈리지 마요와 md_notes 에 둔다. 교안 밖 추론은 레이어 제목에 ‘(추론)’·‘보충(교안 밖)’으로 표시한다.
12. 같은 사실을 한 쪽에서 반복하지 않는다: 정의·인용은 한 번만 쓴다. 우측 요약 패널이 다시 보여 주므로 본문 끝에 다시 정리하지 않는다.
13. `div.sum` 은 한 문단으로 쓰지 않고 세 칸으로 나눈다. ‘외울 규칙’ 목록에 조건 → 결과 규칙을 `<b>조건</b> → 결과` 한 줄씩 쓰고, ‘이유’에는 원리·성립 조건을 1~2문장으로, ‘헷갈리지 마요’ 목록에는 혼동 구분과 범위·판본·예상값 같은 주의를 둔다. 마크업은 아래 ‘요약 세 칸’과 같다.

선례는 `복습노트/실험09` 전체 토픽(읽기 방식 v1 첫 적용)이다. 근거는 2026-11-14 실험09 시안 검토다. 학생 입장에서 문장 하나하나는 쉽지만 핵심 문장이 강조 없이 문단 끝에 묻히고, 같은 정의가 본문·규칙표·추적표 앞 문단·요약 패널에 반복되어 집중이 흐려진다고 판단했다. 시안은 본문을 약 40% 줄이고 규칙표를 빼고 결론 소제목·핵심 문장·이유 열·비교 행을 넣었으며, 사용자가 그대로 정식 적용하기로 했다. 그 전의 규칙 먼저 순서(2026-10-27 실험06 `t-sr-enable`·`t-d-latch`, 규칙표를 바로 받아들였다는 반응)는 note_reading_version 이 없는 기존 팩에 남아 있고, 그 팩을 부분 수정할 때는 새 순서를 소급하지 않는다. 첫 토픽 `t-start`도 v1 에서는 레이어로 쓰고 결론 소제목·핵심 문장 규칙을 따른다. 동기 흐름은 아래 절을 따른다.

## 독자가 재현할 한 단계

새 팩·전체 갱신과 기존 팩에서 수정한 설명에 적용한다. 새 회로 연결·극성·엣지·조작을 처음 적용하는 곳에서 **조건 → 중간 신호나 조작 → 결과**를 대표 행 하나로 보여 준다. 독자는 같은 규칙을 다음 입력에 한 번 적용해 볼 수 있어야 한다. 그 행을 읽기 전에 필요한 초기값, 비트 순서, 유효 입력과 그림의 신호 이름을 소개한다. 조작표에는 주소 변경 전에 쓰기 해제처럼 순서를 어기면 상태가 달라지는 중간 조작을 넣는다. 이상 모델의 가정은 그 식이나 표를 읽는 자리에서 먼저 밝힌다.

- JK 래치는 Enable이 열린 첫 반전 뒤 새 Q가 어느 NAND로 돌아가 다음 반전을 만드는지 보여 준다.
- 74670은 쓰기 직후 WE를 1로 올리고 새 주소와 데이터를 맞춘 뒤 WE를 0으로 내린다.
- DAC는 정확한 1·2·4·8 계단의 전제와 실제 결선에서 가산 노드 전압을 올렸을 때 달라지는 가지 전류를 밝힌다.

## 첫 토픽: 회로를 쓰는 이유

`t-start`의 제목은 ‘왜 이 회로를 쓰는지 먼저 알아봐요’로 쓴다. 앞부분의 새 동기 설명은 약 2~4개 짧은 문단으로 아래 흐름을 연결한다. 기존 수행 범위·판본·예상과 측정 구분은 이어서 보존한다. note_reading_version=1 에서는 첫 레이어 제목과 p.gist 로 해결할 문제를 먼저 말하고, 작은 예는 추적표로, 이번 실험과의 연결은 실험|칩|크기|확인할 것 표로 쓴다. 수행 범위·판본·예상값 고지는 div.sum 의 헷갈리지 마요와 md_notes 로 옮긴다.

1. 해결할 문제: 무엇을 판단·계산·선택·변환하려는 상황인지 먼저 보여 준다.
2. 회로가 필요한 이유: 단순한 연결이나 기존 방식에서 어려운 점과, 이 회로가 해결하는 일을 설명한다.
3. 작은 입력·출력 예: 신호 이름과 0·1의 의미를 설명하고 실제 값 한 가지를 따라간다. 조건·극성·초기 상태가 필요한 경우 생략하지 않는다.
4. 이번 실험과 연결: 무엇을 바꾸고 관찰하면 그 역할을 확인할 수 있는지 설명한다.

정의, 핀 암기, ‘시험에 나와요’만으로 동기를 대신하지 않는다. 활용 사례를 교안의 주장으로 꾸미지 않는다. 직접 구성한 상황은 ‘이해를 위한 예시’, 교안 밖 원리는 ‘보충’으로 표시한다. 이상적인 모델의 예와 실제 IC의 극성을 구분하고 실제 측정값을 만들지 않는다. 비유는 실제 신호에 대응시킨다. 상세 식과 진리표는 뒤의 개념 토픽에 둔다. 첫 토픽의 `div.sum`에도 해결하는 문제를 포함한다.

## 생명과학과 동일한 화면
assets/note-template.html, review-template.html은 생명과학에서 가져온 화면을 사용한다. 원래 upstream 해시는 template-provenance.json의 sha256에 보존하고, 로컬 수정의 실제 해시와 이유는 local_adjustments에 기록한다. CSS·색·레이아웃·패널·페이지 이동을 새로 디자인하지 않는다.
토픽은 조립기가 article.topic/h3로 감싼다. fragment 안에는 아래 순서의 layer를 사용한다.
eli5(직관) → formal(정확한 원리·조건) → warn(혼동 방지) → supp(보충, 필요할 때).
각 layer는 div.layer + span.layer-title로 표시한다. 교수 발언 자료가 없으면 prof를 만들지 않는다.
토픽 마지막에 직계 자식 div.sum[hidden]을 둔다. 안쪽은 아래 세 칸을 이 순서로만 쓴다. ‘외울 규칙’은 반드시 두고, ‘이유’·‘헷갈리지 마요’는 담을 것이 없으면 칸째 뺀다. 칸 이름은 제목 요소가 아니라 p.sum-label로 쓴다(우측 중복 제목 금지).

```html
<div class="sum" hidden>
  <p class="sum-label">외울 규칙</p>
  <ul class="sum-rules"><li><b>J=1, K=0</b> → Set (Q=1)</li></ul>
  <p class="sum-label">이유</p>
  <p class="sum-why">…</p>
  <p class="sum-label sum-label-warn">헷갈리지 마요</p>
  <ul class="sum-traps"><li>…</li></ul>
</div>
```

manifest.note_summary_version=2인 팩은 build가 이 구조를 검사해 한 문단 요약·순서 어긋남·빈 목록을 거절한다. 새 팩과 요약을 다시 쓴 팩에 지정한다. 본문의 핵심 개념·작동 원리·성립 조건·혼동 구분을 압축하고 항목 수의 고정 상한을 두지 않는다. 긴 비유·반복·주변 사례는 그대로 복사하지 않는다. 본문에 없는 사실을 요약에만 추가하지 않으며, 보충의 범위·출처·불확실성을 보존하고 같은 토픽의 보충임을 식별할 수 있게 한다. 이 내용이 우측 요약 패널로 이동한다. 중앙 h3와 고정 패널 제목은 유지하고, 우측에 현재 토픽·문항 제목을 다시 만들지 않는다. sum-for ID는 유일한 .sums 컨테이너에 두며 제거한 제목 요소의 JavaScript 참조도 남기지 않는다. 풀이 도움의 힌트·풀이·푼 문제 토글은 유지한다.
요약은 토픽 조각 대신 `sections/note-summaries.json`(`{"schema_version":1,"topics":{"t-d-latch":{"rules":[["D 래치","Q=D"]],"why":"…","traps":["…"]}}}`, `why`·`traps` 생략 가능)에 둘 수 있고, RUN에 있으면 build가 조각의 div.sum을 그 내용으로 바꾼다. 원고에서 다시 빌드할 때는 발행본 `.pack/sections/`의 `table-layout.json`·`note-summaries.json`을 RUN/sections로 복사한다. 이미 발행된 팩은 JSON을 `.pack/sections/`에 두고 `python -m scripts.lab.review_pack.summary_upgrade --folder 복습노트/실험NN`으로 미리 본 뒤 `--apply --backup-dir tmp/…`로 바꾼다. 옛 요약의 숫자·신호명·IC 번호가 빠지거나 동반 MD가 HTML과 어긋나 있으면 도구가 거부한다. 기호(↑↓ − ≠ Ω ⁿ)는 빠지면 잡지만 집합 비교라 ↑↔↓ 맞바꿈과 한국어 사실은 사람이 감사표와 대조한다. note_summary_version=2인 팩은 check가 발행본 요약이 JSON을 그린 결과와 같은지도 본다.
본문과 요약을 바꾸면 기존 동반 MD 및 실제 생성 원고도 동기화한다. 원래 동반 MD가 없는 자료에는 새 MD 형식을 만들지 않는다. [본문–요약 감사와 패널 검증](verification.md#본문요약-감사와-패널-검증)을 따른다.
새 manifest에는 note_presentation_version=2를 지정한다. fragment에 ‘이 개념으로 풀 문제’, 출처 문구·sources 요소를 넣지 않는다. topics[].sources와 included 문제의 topics로 해당 토픽 MD 끝에 출처·문제 링크를 자동 생성한다. 원자료 쪽수·판본 파일명·재제작 대조 기록 등 추가 근거는 topics[].md_notes에 쓴다. 개념 이해에 필요한 불확실성·극성·실험 수행 범위 경고는 HTML 본문에도 남긴다.
설명 그림은 직접 SVG로 다시 그린다. 원문 스캔, 낡은 그림의 확대/덧칠, evidence 이미지를 설명용으로 재사용하지 않는다. 신호 방향·반전 bubble·접속점·비접속 교차·비트 순서·enable 극성을 원문 및 식/진리표와 대조한다. 원문과 도출값 충돌이 있으면 이상 모델임을 설명하고 대조 기록은 MD에 남긴다. 모든 SVG에 viewBox/title을 넣고 외부 이미지 없이 제작한다. 글자는 최소 18px, 선·라벨은 양쪽 테마에서 읽혀야 한다. HTML과 MD는 같은 SVG를 참조한다. 진리표는 텍스트 표로 작성한다.
이미지는 div.figure 또는 figure.figure로 감싼다. 원본 템플릿은 .figure 안의 이미지에만 너비 제한을 적용하므로, 원문·풀이 details 안의 이미지도 같은 규칙을 따른다. 템플릿은 `.figure img`/`.figure svg`·`.work-board img`에 `border-radius: var(--radius)`를 적용해 다크모드에서도 각지지 않게 유지하고, `.tags`가 없는 토픽에서 `.topic h3 + .layer.eli5`에 `margin-top: var(--s5)`를 두어 소제목 상단 여백을 확보한다. 모바일과 인쇄에서 그림의 오른쪽이 잘리지 않는지 확인한다.
표시 버전 없는 기존 기출 fragment는 div.problem, details.original, details.hint, details.solution 순서다. 새 review_presentation_version=2는 [문제지·해설지 작성 계약](workbook.md)의 문항 JSON을 사용한다. 문제에 주어진 그림과 완성 회로를 각각 questions/solutions로 저장하고 텍스트 표·수식을 유지한다.
legacy는 문제·출처 → 필요한 개념 링크 → 힌트 → 단계별 풀이 → 최종 답 → 검산 → 흔한 실수를 제공한다. 워크북 v2 문제·힌트의 링크 금지는 workbook.md를 따르고 필요한 개념 설명은 문제설명 문서에 둔다.
카드 제목은 조립기가 article.card/h3로 붙인다. 번호가 정답 검증 상태를 대신하지 않는다.
객관식 원문이 아니면 객관식으로 바꾸지 않는다. 진리표·부울식·설계·타이밍·계산·서술형을 유지한다.
HTML은 KaTeX용 $...$/$$...$$ 또는 data-tex를 가진 MathML을 지원한다. 형식별 의미가 같아야 한다.
같은 식의 동치 표현과 다른 유효 설계도 인정한다.

위젯은 이해에 필요한 경우에만 넣고 같은 내용을 static-equivalent에 표·그림·설명으로 남긴다.
